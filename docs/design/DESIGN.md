# kokoro-mods: design v0.2.6 (frozen 2026-10-06)

Version trail: v0.2 after the independent design review; v0.2.1 to v0.2.4 after the round inspections of each worker (REVIEW-LOG.md); v0.2.5 after the final inspection of the merged tree (five chunks) and its re-inspection (eight requests, REVIEW-LOG.md), which changed the slug source, the leak-check needles, the publish-guard polarity rules, the generated module's option handling, the checker's normalisation order and the acceptance wording below; v0.2.6 after twenty-one re-inspection rounds of the matcher, the catalog and the content check (REVIEW-LOG.md, the first all-pass round being the twenty-first), which rewrote the publish-guard polarity (two clause scopes, confirmations put off, a person's say-so as the default gate), the quiet-confirmations negations and the checker's quoting rule, the real manual's proposal set staying the same throughout.

kokoro-mods reads a person's AI user manual (a `kokoro.md`, a `torisetsu.md`, or a loosely structured profile such as a HUMAN.md) and proposes Claude Code function-hook plugins ("mods") that make the harness behave the way the manual asks. The person reviews the proposals, installs what they choose, and the mods count what they did so the effect can be checked later. When the manual changes, the same command shows the proposed rewrite as a diff before replacing the previous output.

This document is the contract for the implementers (one worker per work package, §10) and for the reviewers. Shapes marked **frozen** must be implemented exactly; anything else is the implementer's call. v0.2 folds in the 33 findings of the design review (`docs/design/REVIEW-LOG.md` says what was done with each).

## 1. Target and value

Target for the first public release (needs survey, `docs/research/2026-10-06-needs-survey-astra.md`, option ②): people who use Claude Code regularly and keep asking it for the same accommodations ("answer first", "don't correct my typos", "ask before you push", "tell me when it's still running"), and who can write those accommodations down in a short manual. People who hold a psychologist-translated `kokoro.md` (option ①) are the clinical on-ramp and are served by the same code path. People without a manual (option ③) are pointed to `ai-torisetsu` to write one.

One line: **Spend less effort repeating how you want Claude Code to work.**

Why this exists when ADHD skills already exist (`docs/research/2026-10-06-prior-art.md`): every existing tool takes a label in and emits one fixed rule set. kokoro-mods takes the person's own words in, emits hooks that can enforce, draw, time and count, cites the exact line for every proposal, never applies anything by itself, and never sends the manual anywhere.

## 2. Principles (each has an automatic check, §8)

1. **Profile-driven.** Every proposal cites a verbatim line of the manual that triggered it. No diagnosis label is read; the forbidden-content rules of the KOKORO spec (§7.1) make the tool refuse a manual that contains one.
2. **Deterministic and offline.** No model call, no network, no child process except `claude plugin validate/test` in the integration tests. Same input, byte-identical output.
3. **Proposal, not application.** Output goes to a folder the person names. Nothing under the home directory is written. Installing is the person's own `/plugin install`.
4. **Bounded.** At most three proposals are enabled by default; the rest are present but off, as toggles. Notifications have a shared cooldown.
5. **Counted, not narrated.** Mods record counts (events per recipe), never prompt text, answer text, tool output or manual text.
6. **Nothing from the manual enters the distributable.** The plugin folder carries recipe text and bounded parameters only. The manual's lines appear only in the two report files, which live outside the plugin folder and are rendered inert.

## 3. User flow

```
kokoro-mods check   profile.md                       # content and structure check (exit 0 / 3)
kokoro-mods propose profile.md --out ./mods/me       # writes ./mods/me/plugin/ (distributable) + ./mods/me/PROPOSALS.md + PROPOSALS.json (private)
#   -> read PROPOSALS.md, then inside Claude Code:
#      /plugin marketplace add ./mods/me/plugin   and   /plugin install kokoro-mods-me
#   -> toggle recipes in /config (each is a userConfig row)
kokoro-mods propose profile.md --out ./mods/me       # later, after editing the manual: prints the rewrite diff, then replaces the files it owns
kokoro-mods diff old/PROPOSALS.json new/PROPOSALS.json
#   inside Claude Code: /kokoro-mods status | export <absolute path> | export --print | allow-publish [minutes] | focus <minutes> | reset
kokoro-mods report export.json [export-before.json] [--settings ~/.claude/settings.json]
kokoro-mods recipes
```

## 5. Data contracts (frozen)

### 5.1 Profile (output of `parseProfile`)

```js
{
  format: 'kokoro' | 'torisetsu' | 'generic',   // frontmatter `format`, else `format_version` (the key the KOKORO spec uses), starting with kokoro / torisetsu; else 'generic'
  language: 'ja' | 'en',                         // frontmatter `language` when ja/en, else CJK ratio >= 0.2 -> 'ja'
  frontmatter: { [key: string]: string } | null, // flat `key: value` lines between the leading `---` fences
  title: string | null,                          // first `# ` heading
  sections: [ { num: number|null, key: SectionKey, heading: string, startLine: number, endLine: number } ],
  lines: [ {
    line: number,            // 1-based line number in the file
    section: SectionKey,     // 'unknown' before the first heading
    sectionIndex: number,    // index into `sections` (-1 before the first heading); the stable way to tell sections apart when keys repeat
    kind: 'frontmatter' | 'heading' | 'bullet' | 'row' | 'text' | 'comment' | 'code' | 'blank',   // frontmatter lines and fenced code lines are never matched and never quoted (F rules still scan their raw text)
    raw: string,             // the line exactly as in the file (no newline)
    quote: string,           // `raw` with every inline HTML comment removed (equals `raw` when the line has none); what evidence quotes, so a private comment inside a bullet is never quoted
    text: string,            // content without list marker / table pipes / blockquote marker, trimmed; '' for blank and comment
    depth: number,           // bullet nesting depth (0 for everything else)
    cells?: string[], left?: string, right?: string,   // table rows: every cell trimmed; left/right = the first two (the DO/DON'T table of §5)
    inExample: boolean       // true inside a `###` subsection whose heading contains an EXAMPLE_HEADING_MARKERS entry
  } ]
}
```

`SectionKey = 'boundaries' | 'about' | 'strengths' | 'style' | 'care' | 'weak' | 'focus' | 'decision' | 'history' | 'unknown'` (values and the number map live in `src/constants.mjs`). `parseProfile(text)` takes the text alone (the file name is not part of the profile).

Section detection: `## N. title` (ASCII or full-width stop) maps by number (`SECTION_BY_NUMBER`). An unnumbered `##` heading maps by keyword (`HEADING_KEYWORDS`, case-insensitive substring, first key in object order wins; nothing → `unknown`). `###` headings do not start a section; when the `###` text contains an `EXAMPLE_HEADING_MARKERS` entry, every line until the next `##`/`###` is `inExample: true`. HTML comments (`<!-- ... -->`, one line or several) become `comment` lines when the line is nothing but comment; an inline comment inside a line of another kind is removed from `text` and `quote` (the kind stays). Comment lines are never matched and never quoted, but scanned by the forbidden-content check. A `generic` profile with no `##` heading at all has every line in section `unknown`; it is still usable (low-confidence proposals).

`text` is produced by stripping markers from the ends only (list marker, `> `, table pipes, surrounding spaces) and removing an inline HTML comment (`<!-- … -->` inside a line leaves the line's kind unchanged; only a line that is nothing but comment is `comment`); inner characters are otherwise never altered. For a `row`, `text` is `cells.join(' | ')` (so `text` is **not** a substring of `raw` for rows; evidence therefore quotes `quote`, §5.4). A table starts only at a line that has outer pipes, or at a piped line immediately followed by a separator row (`|---|`); a prose line that merely contains `|` is text. Parsing details that the content check depends on (frozen): the text is NFKC-normalised for matching and checking (full-width `ＡＤＨＤ` is `ADHD`; curly apostrophes become `'`) while `raw` keeps the original bytes; a UTF-8 BOM and CRLF line ends are tolerated; frontmatter is the block between a first-line `---` and the next `---` within the first 40 lines whose inner lines are all `key: value`, blank or `#` comments (otherwise there is no frontmatter and a later `---` is a horizontal rule); frontmatter values may be quoted; `format` is `kokoro` when the value is `kokoro` or starts with `kokoro/`, likewise `torisetsu`; `format` is matched case-insensitively; `language` is case-insensitive and `ja-JP`/`ja_JP` count as `ja`, `en-US`/`en_GB` as `en`; a `<!--` inside backticks does not open a comment; fenced code (``` or ~~~) is `code`; a tab indents a bullet like two spaces and `depth` is an integer (`floor(indent / 2)`); a numbered `## N.` heading maps by number in `kokoro`/`torisetsu` profiles, and in a `generic` profile by keyword first and by number only when the keyword gives `unknown`.

### 5.2 Finding (output of `checkProfile`)

```js
{ level: 'FAIL' | 'WARN', rule: string, line: number | null, message: string }
```

Rules and their complete patterns are in **Appendix A** (frozen; ids `F-DIAGNOSIS`, `F-TEST-SCORE`, `F-SELF-HARM`, `F-OVERRIDE`, `F-ROLEPLAY`, `F-STRUCTURE`, `W-NEG-LABEL`, `W-THIRD-PARTY`, `W-FEW-SECTIONS`, `W-NO-SECTIONS`). The F rules scan every line including comments (fail closed). `F-STRUCTURE` applies only to `kokoro` and `torisetsu` formats with zero recognised sections (sections whose key is `unknown` do not count); a `generic` profile with zero sections gets `W-NO-SECTIONS`; `W-FEW-SECTIONS` counts recognised sections too. The message names the rule and the matched token only, never the whole line (`F-DIAGNOSIS: forbidden term "ADHD"`). Findings are sorted by line (null last), FAIL before WARN on the same line.

### 5.3 Recipe (one entry of the catalog)

```js
{
  id: 'lead-with-answer',                       // kebab-case, unique, frozen in §6
  title: { ja: string, en: string },
  summary: { ja: string, en: string },          // one sentence: what the mod will do
  sections: SectionKey[],                       // sections where a hit is 'high' confidence
  triggers: [ { lang: 'ja'|'en'|'any', pattern: RegExp, cell?: 'left'|'right'|'any' } ],   // cell: which table cell a row trigger reads (default 'any')
  unless:   [ { lang: 'ja'|'en'|'any', pattern: RegExp } ],   // a line matching any of these is not a hit (negation and polarity, §6); applied regardless of the profile language (safe side; `lang` is informational)
  mechanisms: ('prompt.compose'|'prompt.submit'|'tool.call'|'turn.start'|'turn.complete'|'session.start'|'ui.status'|'ui.toast'|'ui.log'|'clock'|'command'|'store')[],
  template: 'compose-rule'|'submit-detector'|'publish-guard'|'running-indicator'|'resume-brief'|'focus-timer',
  priority?: 'safety',                          // a safety recipe (publish-guard) ranks first and is enabled by default whenever it matches
  rule?: { en: string },                        // compose-rule recipes: the imperative sentence(s) injected; placeholders {min} {max} {max_lines} (numbers), {language} (filled with the language NAME: Japanese / English), {max_chars_clause} (filled with '' when max_chars is 0, else ' and within N characters')
  note?: { en: string },                        // submit-detector recipes: the context line attached to a detected prompt
  params: { [name]: { type: 'number'|'boolean'|'string', default, title: {ja,en}, description: {ja,en}, min?, max?, multiple?: boolean, options?: string[] } },
  deriveParams?: (hits, profile) => Partial<params values>,   // may return ONLY bounded numbers (clamped to min..max) and strings that are one of `options`; never free text
  evidence: [ { kind: 'prior-art'|'research'|'author', ref: string, note: string } ],
  metrics: string[],                            // event names this recipe may count (see EVENT_NAMES in the catalog)
}
```

No `title`, `summary`, `rule`, `note` or `description` text may contain a forbidden term of Appendix A (en list); a catalog test checks it.

### 5.4 Proposal and PROPOSALS.json

```js
Proposal = {
  recipeId: string,
  confidence: 'high' | 'medium' | 'low',
  evidence: [ { line: number, section: SectionKey, quote: string, matched: string } ],  // quote === the line's `quote` (raw minus inline comments); 1..3 entries, never empty
  params: { [name]: value },                    // defaults merged with deriveParams (§5.4a)
  enabledByDefault: boolean
}
Bundle = {                                      // PROPOSALS.json (no timestamps: output must be deterministic)
  tool: { name: 'kokoro-mods', version: string },
  profile: { file: string /* basename */, format, language, version: string|null /* frontmatter */, sha256: string },
  pluginName: string,                            // 'kokoro-mods-<slug>': the stable identity of an output folder; the sha256 changes with every edit, the pluginName does not
  proposals: Proposal[],                         // ranked (§5.4a)
  notMatched: string[],                          // recipe ids with no evidence, sorted
  files: string[]                                // every path kokoro-mods wrote under <out>, relative, sorted (what a re-run may replace)
}
```

### 5.4a Ranking and parameters (frozen)

- Candidate lines: `kind` in `bullet`, `row`, `text`; never `comment`, `heading`, `blank`; never `inExample`; never in section `history`.
- A recipe hits a line when some trigger whose `lang` is `any` or equals `profile.language` matches the line (`text` for bullets and text; for rows the cell the trigger names: `left`, `right`, or both for `any`) and no `unless` pattern matches **the same text the trigger matched** (for rows, the cell; a negation written in the left "avoid" cell never cancels a trigger that read the right cell). Every trigger that can read a row names its `cell` explicitly; `left` is allowed only for quiet-confirmations, offer-options, one-next-step, plain-language and trace-offers, and only for wording that names the thing to avoid (a noun phrase such as 「長い前置き」, never a negated verb). For `publish-guard` the catalog carries no `unless`: the matcher judges the polarity of the cell the trigger read (`publishPolarity`, exported for the tests). A waiver phrase (「確認不要」「確認せずに」「了承は不要」「確認は後でいい」「確認は後にして」「確認は一旦後にして」「確認は後回しで」, "without asking", "no confirmation needed"; 「確認後にして」 without the particle and 「確認が済んだ後で」 with a verb before 後 ask first, 「後回しにしないで」 asks to keep confirming) is considered only when its clause names a publishing action (push・プッシュ・公開・publish・PR・プルリク・issue・release; 「テストは確認なしで回してOK」 says nothing about the gate), and it opts the cell out only when its clause grants permission explicitly: a permission word (いい・OK・構わない・大丈夫・自由に, fine・ok・go ahead・feel free・you can/may・not needed・optional; OK and ok are whole words; 「勝手に」 is not one, being a complaint as often as a permission), an imperative to publish without asking that ends the clause (「確認せずにpushして」 "Publish without confirmation."; the plain form 「確認せずにpushする」 is a habit as often as an order and is not one, nor is a gerund subject such as "Pushing without asking has burned me"), or a phrase that states the opt-out itself as a predicate that ends its clause (「確認は不要」「pushは確認しない。」「pushの許可なし」 "do not ask before" "no confirmation needed" "I don't want confirmation"; a bare 「確認なしの…」「確認せず …」 or "no confirmation broke prod" is not one) **and** when its sentence, with every waiver phrase removed, carries no prohibition (やめ・ダメ・NG・厳禁・禁止・いけない・許さ・困る・困ります・なりません・しないで・するな・される, a negated permission in plain or polite form such as 「大丈夫じゃない」「大丈夫ではありません」「いいとは思わない」「いいとは思いません」「いいわけがない」「良くありません」「言ってない」 "isn't ok" "isn't really ok" "hardly ok" "can't" "may not" "don't think", a bare "don't", a bare "isn't"/"is not" anywhere in the sentence ("isn't something I'm OK with"), forbid・prohibit・avoid・stop・must not・should not・never・not ok/allowed/fine). A clause that is a question (「確認不要ですか？」「大丈夫でしょうか」「大丈夫だろうか」「大丈夫か。」, a 「かどうか」 in predicate position (「かどうか迷う」) or a "whether" before the waiver ("push without asking whether I've reviewed it" is a waiver), "You can push without asking? No." "…, right?"; an order's own tag "…, OK?" 「pushして、OK？」 is not one), a first-person habit (「私はpushの前に確認しない」 "I never ask before pushing"; a wish such as "I don't want confirmation" still counts), or speech with a speaker, the speaker being an existence predicate (人・方・同僚・上司・メンバー・チーム… + いる/いた/多い, 声・話・噂・意見 + ある: 「pushしてね、という人がいる」「OKって言う同僚もいる」「という声がある」「と言われた」 "some people say you can"; a policy 「いいという方針にします」「、という方針です」「、という方向で」「という方式」 or a request 「、と頼みます」 is the person's own) states no opt-out and grants no permission; advice against (「しない方がいい」「避けたほうがいい」), an outer negation ("nobody said you can", 「なんてことはない」) and "no longer" are prohibitions; いい/よい count as permission only as a predicate and not after 「ほうが」 (advice) or inside かわいい; "issue" is a publishing object only as something filed (立てる・作成・出す・起票・開く・投げる・切る but not 切り分ける, open/file/create/raise/post/submit a new issue, also filing or creating issues). Permission, a question and reported speech are read in the clause (clauses end at `.!?;,` 。！？、, a line break, parentheses — and at but/however and けど・けれど・ですが・だが, with or without a 、: 「レビューは後でいいけど公開は私がチェックしてから」 keeps its gate); an imperative must end the tight clause, which also ends at "and" ("Just push without asking and I'll check it afterwards" and "You can push and open PRs without asking" are waivers), a Japanese explicit waiver ends its clause and an English one stands anywhere in the tight clause, the first-person habit is read in the tight clause, and the publishing object is looked for there, or, when the waiver phrase is the whole of its tight clause (a please/just/simply/then/ok before it allowed), in the order that an "and" opens right after it with no comma between, the order being a push or publish and not a noun phrase ("Don't ask me and just push." waives; "Feel free to run the linter without asking and push when it passes" and "No approval needed and publishing notes is up to you" waive nothing); prohibition is read in the sentence (`.!?` 。！？ and a line end), so 「確認せずにpushするのは、絶対にやめて」 keeps its gate. A waiver opts its whole cell out unless another sentence of the cell asks for the gate: a sentence with no waiver phrase that matches one of the recipe's own triggers asks ("Never push unless confirmed. Feel free to file issues without asking." keeps the gate at medium confidence; the asking vocabulary is the catalog's own, so it cannot drift from it), and so does what remains of a sentence once its waiver clauses are blanked, when a trigger still matches it and it is more than a bare time clause ("Wait for my go-ahead before pushing, but you can open new issues without asking", 「pushは、私がいいと言ってから、イシューは確認なしで立てていい」 keep the gate; "Before you push, push without asking." and 「pushする前に、確認せずにpushして」 are waivers, their remainder being the bare time clause; no second asking vocabulary is kept) and a prohibition with no asking form (「mainへpushしないで。イシューは確認なしで立てていい。」) is not a request for the gate, since the guard implements asking before publishing, not a ban on a branch. Every other waiver is a negated waiver, i.e. a request for the gate (the uncertain side falls towards proposing the safety mod). 「確認せずにpushしないで」「確認なしのpushはNG」「確認せずにpushするのはやめて」「確認不要でpushするのはダメ」, "Don't push without asking", "Pushing without asking is not OK", "Without asking, never push", "Ask before pushing — never ever push without asking" are hits; when one cell both asks for and waives confirmation, the guard wins (hit, confidence capped at medium). "push notifications" and 「push通知」 exclude only that object, never the line. A `cell: 'left'` trigger reads table rows only: in a bullet, 「一案だけ出して」 is a request for the thing itself.
- Confidence: `high` when the section is in `recipe.sections` and the format is `kokoro` or `torisetsu`; `medium` when the section is elsewhere, or for any hit in a `generic` profile with a known section; `low` when the section is `unknown`.
- Evidence: the first three hits in line order, except that a hit whose line contributed a derived parameter, and the first hit that determined the proposal's confidence, are always included (each replaces the last entry when the cap is reached) so every value and the confidence can be traced to a quoted line; `quote = line.quote`, `matched` = the matched substring of the text that matched.
- Order: safety recipes (`priority: 'safety'`) first, then confidence (high > medium > low), then evidence count (descending), then catalog order. `enabledByDefault = true` for the first `maxEnabled` proposals only (default `DEFAULT_MAX_ENABLED` = 3; 0 allowed; `Infinity` allowed via `--all`); a matched safety recipe is therefore on by default unless `maxEnabled` is 0. `maxEnabled` must be a non-negative integer or `Infinity` (anything else throws a `TypeError`).
- Params: the recipe defaults, overridden by `deriveParams(hits, profile)`; a derived number is rounded to an integer and clamped to `min..max`; a derived range with min > max is ignored; a derived string not in `options` is ignored; when several hits derive different values, the first hit in line order wins.
- Same profile → deep-equal proposals.
- Slug (`slugFor`): the `--name` option only, NFKC-normalised, lower-cased, reduced to ascii letters/digits/hyphens (runs collapsed, hyphens trimmed, at most 40 characters). The manual's title, `name` and `user_alias` are never used: the plugin name enters the distributable and every export, and those fields may carry a person's name (final inspection, chunks C and E). Without `--name` the slug is `profile` and `slugSource` reports `fallback` (the CLI prints a naming hint after a successful run); a `--name` that is given but empty after normalisation, or that contains a forbidden term of Appendix A's English list (as a word for every term except ADD, OD and DAN, which are ordinary lower-case words; the longer terms ADHD, FSIQ, PTSD, ICD-10/11, F-codes, autism/autistic, dyslexia/dyslexic, bipolar, schizophrenia/schizophrenic, asperger also inside a word) is `rejected` and the CLI refuses it with a usage error (exit 2) rather than replacing it. The plugin name is `kokoro-mods-<slug>`; `isPluginName` (the shape `PLUGIN_NAME_PATTERN` of `src/constants.mjs`, `^kokoro-mods-[a-z0-9]+(?:-[a-z0-9]+)*$` at most 52 characters, plus the same term rule) is enforced by the emitter, the bundle check of the CLI and the export validator.
- Derivation sources (frozen, from the catalog inspections): `lead-with-answer.max_chars` is derived only when a reply word (回答|返答|答え|説明|返事|応答, answers?|responses?|repl(y|ies)|explanations?) stands within a dozen characters (ja, a 、 allowed) or 24 characters (en) before the count, the unit is 文字 or 字 (chars/characters), and a bound word follows (以内|程度|まで|くらい, under|within|max|at most): 「返答は200文字以内」 derives, 「ブランチ名は30字以内」「コミットメッセージは50字以内」 do not; a limit whose clause names another object (件名・コミット・タイトル・題名・見出し・ファイル名・ブランチ名・変数名・関数名・要約文・コメント・PR and their English counterparts, within 16 (ja) or 24 (en) characters before or after the count, a comma ending the clause) is refused by the trigger and by the derivation themselves, not by `unless`, so 「ブランチ名は30字以内。結論を先に。」 and 「件名は英語、回答は200字以内」 still propose (the latter with its limit); a 、 is allowed only right after the reply word (「回答は、200字以内」), so 「回答は日本語で、引用は200字以内」 derives nothing (§6); `response-language` takes the language from the capture of the trigger that matched (`(日本語|英語|私の言語)で(返|答|応答)`, `常に(日本語|英語)で(返|答|応答|話)`, `(返答|回答|応答)(は|を)(日本語|英語)`, `(respond|reply) in …`, `(always )?answer in …`), not the first language name in the line, so 「コードのコメントは英語で、返答は日本語で」 and 「常に英語の資料を読むが、返答は日本語で」 → ja; `focus-timer.interval_minutes` only from `(\d+)\s*分(ごと|おき|毎|間隔)`, `every (\d+) ?min`, `(\d+)\s*(時間|hours?)` × 60, or 「タイマーを N 分で(入れ|掛け|かけ|使)」 (a timer set to N minutes names the interval; added at the final pass), on a line that mentions 休憩|タイマー|ポモドーロ|break|remind|timer|pomodoro; 「5分の休憩を1時間ごとに」 → 60.

### 5.5 Generated output (frozen layout)

```
<out>/plugin/.claude-plugin/plugin.json        name, version, description, author {name:'kokoro-mods'}, license 'MIT', keywords, userConfig
<out>/plugin/.claude-plugin/marketplace.json   { name: <pluginName>, description, owner: { name: 'kokoro-mods' }, plugins: [ { name: <pluginName>, source: './' } ] }  (description is required by --strict)
<out>/plugin/hooks/hooks.json                  { "modules": ["./register.ts"] }
<out>/plugin/hooks/register.ts                 the hooks module (§7)
<out>/plugin/hooks/register.test.ts            tests run by `claude plugin test` (§7.1)
<out>/PROPOSALS.md                             private report: per proposal the quoted lines (inert, inside fenced code blocks), what the mod does, toggles, counts, evidence
<out>/PROPOSALS.json                           the Bundle (private)
```

`plugin/` is the distributable (what `/plugin marketplace add <out>/plugin` reads); nothing from the manual is in it (A5). Two mechanisms enforce that inside the emitter (frozen): (1) the manifest, module and test templates receive the bundle with every `evidence` removed, and a string param without `options` (single or `multiple`) is accepted only when it deep-equals the recipe's default (any other value throws: free text cannot reach `plugin.json`); (2) before returning, `emitPlugin` runs `leakCheck` over `plugin/**` with the needles of `leakNeedles`: every `quote` and every `matched` of the bundle, NFKC-folded and lower-cased, of at least two characters, except those that the catalog's own text, the templates' source or the plugin name contains (such text, "push", 確認, a line that is word for word a recipe title, occurs in the distributable legitimately and reveals nothing beyond which recipes matched, so it cannot evidence a leak; the earlier twelve-character floor was dropped at the re-inspection because a line equal to a title would have failed a legitimate manual). `leakCheck` folds the files the same way and also searches the JSON-escaped spelling; any hit throws `E_LEAK` naming the file and the evidence position (`proposals[i].evidence[j]`), never the text. The templates receive a bundle rebuilt additively from the known fields only (`stripEvidence`). Before rendering, `emitPlugin` refuses a bundle whose `pluginName` fails `isPluginName` (`E_PLUGIN_NAME`), or whose `profile.sha256` is not 64 hex digits, whose `tool.version` is not a version, whose proposals lack a boolean `enabledByDefault`, a confidence, a params object or evidence objects, whose params carry a key the recipe does not declare or lack a declared one, or whose `patterns` list is empty, holds a non-string or a pattern that does not compile in Unicode mode (`E_BUNDLE`; a shipped guard must never deny every command because of a catalog or bundle defect). The manifest and marketplace descriptions carry the profile's sha256 prefix only, never the file name. `userConfig` keys: `snake(recipeId)` (boolean, `default` = enabledByDefault) and `snake(recipeId) + '_' + param` (snake = hyphens to underscores). Every field carries `type`, `title`, `description`; numbers carry `min`/`max` when the recipe declares them; `multiple: true` only on string params (array of strings, typed `readonly string[]` in the module); `options` only on non-multiple strings. `title`/`description` use the language of the profile (`--lang` overrides). The golden plugin in `docs/design/golden/plugin/` is the generator's own output for `fixtures/valid/en-generic.md` with `--name golden`; a test keeps it byte-identical to a fresh run, and it is validated with `claude plugin validate --strict` and `claude plugin test` (Claude Code 2.1.290 and 2.1.291) in CI and in the integration tests.

Re-run on an existing `<out>`: when `PROPOSALS.json` exists with the same `pluginName`, print the diff (§5.7), then replace exactly the paths listed in its `files` (write to a temporary sibling folder, then move into place); other files in `<out>` are untouched. A different `pluginName` → exit 5 unless `--force`.

### 5.6 Metrics and export (frozen, closed schema)

The mod keeps one object in `$.store` under `STORE_KEYS.metrics`:

```js
{ v: 1, since: number /* epoch ms */, counts: { [recipeId]: { [event]: number } } }
```

Increments are serialised through one promise chain inside the module (a read-modify-write that overlaps would lose counts); `export` awaits the chain first. `/kokoro-mods reset` clears `counts` and sets `since`.

Export object (what `/kokoro-mods export <absolute path>` writes and `export --print` returns as text):

```js
{ v: 1, plugin: string, profileSha256: string /* 64 hex */, exportedAt: string /* ISO 8601 */,
  options: { [userConfigKey]: boolean | number },    // string params (phrases, patterns, language) are NOT exported
  metrics: { v: 1, since: number, counts: { [recipeId]: { [event]: integer >= 0 } } } }
```

`src/metrics.mjs` exports `assertMetricsExport(obj, sets)` and `exportSets(RECIPES)`, which builds the sets: `recipeIds`, `eventNames`, `optionKeys`, `optionTypes` (a toggle is a boolean, a numeric parameter a finite number) and `recipeEvents` (each recipe may count only its own `metrics`, plus `suppressed` for the two toast templates). The validator throws unless every key is one of the allowed sets, `plugin` passes `isPluginName` (shape and no forbidden term), every option has its declared type and every count is a non-negative safe integer; any other field, nested field or string is a defect. An unknown key is reported by its position (`$.options: unknown key at index 3`), never by name, because its name is input; allowed keys are named, and the CLI prefixes the argument (`export:` or `before:`) so a report with two exports says which one failed. `report` with two exports refuses exports of different plugins (`E_EXPORT_MISMATCH`, exit 1) and warns on stderr when `profileSha256` differs.

### 5.7 Diff (frozen)

```js
diffProposals(before, after)  // Bundle or { proposals } inputs
  -> { added: string[], removed: string[], changed: [ { recipeId, fields: ('params'|'evidence'|'enabledByDefault'|'confidence')[] } ], same: string[], hasChanges: boolean }
```

Ids sorted in every array; `evidence` compares the sequence of `quote`s; `params` deep-equal. `formatDiff(diff, { lang })` renders it for the CLI.

## 7. Generated module (`hooks/register.ts`)

Frozen structure; the implementer writes the bodies. `docs/design/golden/plugin/hooks/register.ts` shows the proven idioms (section append, deny before `next`, context attach, `.catch` on every gating hook).

```ts
import type { Register } from 'claude-code'
type Options = { /* one field per userConfig key, typed; string multiple -> readonly string[] */ }
const PLUGIN = '<pluginName>'
export const register: Register = (on, options) => {
  const o = options as unknown as Options
  // metrics: one promise chain; bump($, recipe, event) never throws
  // 1. prompt.compose (only when a compose-rule proposal exists): const r = await next(e); return { sections: [...r.sections, { id: PLUGIN + ':profile-rules', text, scope: 'session' }] } or r when no rule is enabled
  // 2. prompt.submit (only when a submit-detector proposal exists), with .catch(($, e, next) => next.called ? next(e) : next(e)): stop-signals first, then receive-only; a hit attaches ONE note: return next({ ...e, context: [...(e.context ?? []), NOTE] })
  // 3. tool.call { tool: 'Bash' } (publish-guard): validate options and read the grant BEFORE next; every pattern is compiled (`new RegExp(src, 'u')`) before any is tested, and a list that is empty, not all strings, or holds a pattern that does not compile denies with the fixed invalid-configuration sentence, which says that every Bash command is denied until the setting is fixed (it never silently skips a pattern; the toggle is the way to switch the guard off); a store read that throws denies; .catch(($, e, next) => next.called ? next(e) : { deny })
  // 4. turn.start / tool.call (any) / turn.complete (running-indicator, lead-with-answer counter, resume-brief save); observers wrap their bodies in try/catch and always return next(e)
  // 5. session.start: remember isInteractive and cwd; register the command; resume-brief log; focus-timer start
  // 6. command.run { command: 'kokoro-mods' }: status | export <abs path> | export --print | allow-publish [minutes] | focus <minutes> | reset; every subcommand that writes a file or changes state (export <path>, allow-publish, focus, reset) is accepted ONLY when e.origin.kind === 'composer' (typed by the person); allow-publish minutes is an integer 1..720 (default allow_minutes); status and export --print answer any origin; anything else answers the usage line. Options are validated before use (`normalizeOptions`): a patterns value that is not a non-empty array of strings makes the guard deny with a fixed 'invalid configuration' sentence; a missing or non-finite number falls back to the manifest default, which is the proposal's value (a derived 25-minute interval stays 25), and every number is clamped to the recipe's bounds on each side the recipe declares; a missing or non-boolean toggle falls back to the manifest default (a dropped toggle cannot disarm a guard). Module-level state (the promise chain, interactive, cwd, the toast cooldown, the timers) is reset by `resetState()` at the top of `register`, so a reload or a test runner that registers again starts clean
}
```

`claude plugin validate --strict` treats a gating hook without `.catch` as an error; `prompt.submit` and `tool.call` hooks therefore always carry one. `$.ui.status`, `$.ui.toast`, `$.ui.log`, `$.clock.every` are used only when `session.start` reported `isInteractive`. Nothing in the module reads `e.text`, `e.answer` or `e.command` into the store or into any output except the status line's tool name and the deny text's fixed sentence.

### 7.1 Generated tests (`hooks/register.test.ts`)

Emitted conditionally: test (1) always; the others only when their recipe is in the bundle. Idioms proven on 2.1.290 (golden file): `test(name, { options }, async ($, on) => ...)`; a bottom hook per dispatched event registered with `on`; `$.prompt.compose({ model: 'm', promptModel: 'm', surfaces: [], tools: [], outputStyle: null, traits: [] })` (all fields required); `$.tool.call({ tool: 'Bash', command })`; `$.prompt.submit({ text })`; `mock.store(on, {})`, `mock.clock(on)`.

1. The module loads with the manifest defaults (a compose dispatch answers).
2. compose: with the rule on, `result.sections` ends with `<pluginName>:profile-rules` and keeps the bottom's section first; the section has the heading line plus one rule line per enabled compose recipe and no unfilled placeholder; with every rule off, the bottom's sections come back unchanged.
3. publish-guard: the bottom `tool.call` hook records every command it receives; `git push origin main` is denied (`deny` mentions `allow-publish`) and the bottom never saw it; `ls` passes and the bottom saw exactly `ls`; with a grant in the store (`publishAllowedUntil` in the future, `mock.clock`), `git push` passes.
4. submit detectors: the bottom `prompt.submit` hook records `e.context`; `眠い` arrives with one note; a long ordinary prompt arrives with none; a stop phrase arrives with the stop note only. Every negative case is listed under the detector whose phrase it starts with (「あとでテストして」 with the stop phrases, 「疲れたけどやる」 with the fragments and with the stop phrases), and every such phrase also has a positive case (「あとで」「終わり」 "wrap up"), so each negative proves the whole-utterance guard and not a phrase that never fires.
5. export: the kit dispatches `$.command.run` without a composer origin, so the test first runs `reset` and checks the refusal sentence, then `export --print` answers JSON that parses, whose keys and string values are only those of §5.6 (the test embeds the allowed sets), and whose counts are the seeded ones (nothing was reset).

## 11. Decisions and open points

- **Name**: `kokoro-mods` (KOKORO family: kokoro-mcp, kokoro-edge). The survey notes a search collision with "Kokoro TTS"; alternatives recorded (torisetsu-mods, PacePatch, WorkstyleMods). Renaming before the public release is cheap and is the maintainer's decision.
- **No LLM in the main path** (claude-env-coach v3's lesson: 814 LLM-written proposals, 0 adopted; and the manual must not leave the machine).
- **Status line, not a band**, for `running-indicator` in v0.1 (no JSX, no state contract).
- **Rewriting third-party mods** is out of scope; "rewrite" means re-proposing from a changed manual and replacing the files kokoro-mods owns after showing the diff.
- **Why Node, not Python**: the generated mods are TypeScript, Claude Code users have Node, one toolchain.
- **What cannot be measured**: whether the person felt less load. Counts are proxies; PROPOSALS.md says so.
- **Unprotected paths** (publish-guard): non-Bash tools and scripts that push internally. Stated in PROPOSALS.md.
- **Plugin name from `--name` only** (final inspection, chunks C and E): a manual's title, name or alias can be a person's name and would otherwise enter `plugin.json`, the module and every export; `profile` is the fallback and the CLI says so.
- **Leak needles** (final inspection, chunk C): short quotes and matched words are needles unless the catalog or the templates contain them; a quote of twelve or more characters is always one. A short line that is itself catalog text cannot be told from catalog text, and that limit is accepted.
- **Finding messages name the matched token** (final inspection, chunk E asked for the token to be hidden as well): the person needs the word to fix the line, the token is a catalog term, and §5.2 keeps it; the line itself is never printed.
