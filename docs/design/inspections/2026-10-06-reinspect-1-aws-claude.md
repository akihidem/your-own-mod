## 2. 指摘

### high（重大）

**H-1　`src/match.mjs` `publishPolarity`：`EXPLICIT_WAIVER` の先読みが効いていない**

- **問題：** `EXPLICIT_WAIVER.test(matched)` は、切り出した一致部分だけを検査しています。そのため `(?=[。、！？\s]|$)` の `$` が一致部分の末尾で必ず成立します。「確認なし」「確認せず」「確認しない」はすべて明示の許可として扱われます。
- **例：** 「確認なしのpushが心配」「確認せずにpushしてしまう癖がある」は禁止語を含みません。このため確認の放棄と判定され、確認を求める表現（ask）も無いので、安全 mod が提案から消えます。
- **修正：** 一致部分ではなく、元の文の一致位置から節の終わりまでの部分に対して検査してください。

**H-2　同関数：許可語そのものの否定を見ていない**

- **問題：** `PERMISSION` は、許可語が文字列に含まれるかどうかだけを見ています。許可語の直後にある否定を見ていません。
- **例：** 次の文はすべて「許可あり・禁止なし」と判定され、ゲートが落ちます。
  - 「確認なしでpushしても大丈夫じゃない」
  - 「確認なしで公開されるのがいいとは思わない」
  - "Pushing without asking isn't ok"
- **修正：** 許可語の後ろ数文字以内に（じゃない／ではない／とは思わない・言えない／isn't／is not）があれば禁止として扱ってください。あるいは、許可語が節の末尾にある場合だけ許可と認める方法もあります。

**H-3　同関数：`CLAUSE_SPLIT` が禁止語を別の節へ切り離す**

- **問題：** 読点やカンマで節を区切るため、後ろに続く禁止語が確認の放棄と同じ節に入りません。
- **例：** 「確認せずにpushするのは、絶対にやめて」は、節が「確認せずにpushするのは」になり、確認の放棄と判定されます。「Publishing without confirmation — not allowed」も同様です。
- **修正：** 許可語を探すのは節単位のままでよいです。禁止語は文単位（。．！？と改行で区切る）で探してください。

**H-4　`IMPERATIVE_WAIVER`：動名詞の主語を命令として扱う**

- **問題：** `(?:publish|push)(?:ing)?` の `(?:ing)?` により、文頭の動名詞が命令文として扱われます。
- **例：** "Pushing without asking has burned me before" "Publishing without confirmation worries me" はどちらも確認の放棄と判定され、ゲートが落ちます。
- **修正：** `(?:ing)?` を削除してください。加えて、その句の後ろが節の終わりであることを条件にしてください。

**H-5（条件付き）　`hitFor` → `publishPolarity`：表の列の意味を受け取っていない**

- **問題：** 極性判定に、セルがどの列か（「してほしくないこと」の列か）が渡されていません。
- **例：** 「してほしくないこと」の列に「確認なしでpush」と書いた場合、確認の放棄と読まれて提案が消えます。
- **条件：** publish-guard のトリガーがその列を読む場合（`cell: 'any'` など）に限り成立します。catalog が無いので、確定はできません。
- **修正：** `cellsFor` が列の役割も返すようにし、避けたいことの列の文字列は常に「確認を求める側」として扱ってください。

### medium（中）

**M-1　`publishPolarity`：確認の放棄が「公開」に結び付いていない**

- **問題：** 確認の放棄が、公開以外の対象についての文でも成立します。
- **例：** 「テストは確認なしで回してOK、pushは慎重に」「push通知は確認不要」でゲートが落ちます。使われていない `PUSH_NOTIFICATION` は、本来この判定に使う予定だった可能性があります。
- **修正：** 同じ節に公開を表す動詞（push／公開／publish）があることを条件にし、判定の前に `PUSH_NOTIFICATION` に当たる部分を空白に置き換えてください。

**M-2　`PERMISSION`：`OK` に語の境界が無い**

- **問題：** 大文字小文字を区別しないため、book・token・look・notebook の中の "ok" で許可が成立します。
- **修正：** `PROHIBITION` の `NG` と同じく、前後に `(?<![A-Za-z])…(?![A-Za-z])` を付けてください。

**M-3　コメントと挙動が食い違っている**

- **問題：** コメントには "Before you push, push without asking" を「確認の依頼＋確認の放棄（＝食い違い）」として読むと書いてあります。実際には before が `PUBLISH_ASK` に無いため、`asking=false` のまま確認の放棄として扱われ、ゲートが落ちます。
- **修正：** `PUBLISH_ASK` に `before\s+(?:you\s+)?(?:push|publish)` と「(?:push|公開)する前」を追加してください。

**M-4　`buildBundle`：説明書の値がそのまま bundle に入る**

- **問題：** `profile.frontmatter.version` を検証せずに bundle に入れています。bundle が export や metrics に出るなら、説明書の文字列がそこへ届く新しい経路になります。
- **修正：** `/^\d+(?:\.\d+){0,2}$/` に合う値だけを残し、それ以外は null にしてください。

### low（軽微）

- **L-1　`slugChoice`：禁止語の境界判定をすり抜ける。** "adhdtools" "autismhelper" "f840" のように語をつなげると検出されません。修正：4文字以上の語と疾患コードは、境界なしでハイフンを除いた slug に対して検査してください。
- **L-2　`slugChoice`：空の `--name` が却下にならない。** `--name ""` が `fallback` になります。修正：`name !== undefined` なら、空文字でも `rejected` にしてください。
- **L-3　エラー文と使われていない定数。** `buildBundle` のエラー文が recipeId の値をそのまま出力します（M5 の「エラー文はキー名だけ」と食い違います）。`CLAUSE_BREAK` と `PUSH_NOTIFICATION` は定義だけで使われていません。修正：エラー文は位置だけを示す形にし、使わない定数は削除するか M-1 で使ってください。
