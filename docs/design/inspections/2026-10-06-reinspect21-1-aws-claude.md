## 指摘事項

**Medium-1**
- 場所：`src/match.mjs`、`PUBLISH_WAIVER` と `publishPolarity`
- 問題：「後回し」と、今回足した「に回」の直後にある打ち消しを見ていない。「pushの確認は後回しにしなくていい」「pushの確認は後に回さなくていい」（＝先送りせず、いつも通り確認してほしい）を例にとる。まず免除の句が一致する。次に `PERMISSION` が文中の「いい」を許可と読む。`PROHIBITION` にはこの打ち消しの形が無い。結果は waiver=true、asking=false となり、安全ゲートが消える。設計が名指ししているのは「後回しにしないで」だけ。この文は二重否定に近く、手引きに書く文としては少し珍しいので medium とした。
- 修正案：`回し` と `に回` の後に打ち消しの否定先読みを置く。具体的には `(?!にし(?:ない|なく)|さ(?:ない|ず|なく))`。あわせて反例テストを2本足す。

**Medium-2**
- 場所：`src/match.mjs`、`JA_PUTOFF_ADV`（公開行為の形）と `asksBeyondWaivers`
- 問題：「レビューはPRを作った後にして、pushはその後で」では、前の節が「後にして」で終わっているので `EXPLICIT_WAIVER` に当たり、免除と判定される。残る節「pushはその後で」は catalog の trigger に当たらない可能性が高い。また `BARE_TIME_CLAUSE` は「は」を含む形を受けないので、裸の時間節にも当たらない。この場合、push 前のゲートが消える。似た形は前回からあり、今回 M-1 で動詞の活用を足したことで当たる範囲が広がった。trigger 次第なので medium とした。
- 修正案：公開行為を挟む形を採用する時は、残りの節に別の公開対象（push/公開）が出てきたら asking として扱う。またはテストを1本足し、この文がゲートを保つことを固定する。

**Low-1**
- 場所：`src/match.mjs`、`PUBLISH_WAIVER` の `に回`
- 問題：直後の文字を縛っていないので、「後に回答」「後に回収」の頭の部分にも一致する。
- 修正案：`に回(?=[しすさ])` とする。

**Low-2**
- 場所：`src/match.mjs`、助詞なしの形の先読み
- 問題：「確認後でいいので、先にpushして」のように読点が入る場合と、目的語が PR やリリースの場合は免除にならない。どちらもゲートを残す側に倒れるので害は小さいが、記録しておく。
- 修正案：先読みに `[、,]?` と PR/リリース を加えるかどうかを、設計に明記する。

**Low-3**
- 場所：`test/match.test.mjs`、narrow triggers の表
- 問題：「確認は後に回すので先にpushして」の行が2回入っている（既存の行と、追加ブロックの末尾）。また L-1 と、M-1 の「作成した」「切った」を固定するテストが無い。
- 修正案：重複行を消し、上の3件を固定するテストを足す。
